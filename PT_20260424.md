# Penetration Testing Report

**Application:** Damn Vulnerable Web Application (DVWA)  
**Repository:** shiualan/DVWA  
**Report Date:** 2026-04-24  
**Classification:** Confidential — Authorized Security Assessment  

---

## 1. Engagement Overview

- **Assessment type:** Secure Code Review / White-box Penetration Test
- **Objective:** Identify security vulnerabilities, insecure patterns, and architectural weaknesses in the DVWA codebase through static analysis.
- **Scope reviewed:** All PHP source files, configuration files, Docker configuration, database setup scripts, and vulnerability module source code across all security levels (low, medium, high, impossible).
- **Out-of-scope assumptions:** Runtime behavior, network-layer testing, third-party dependency deep-dives (e.g., Composer packages), and infrastructure beyond the Docker configuration provided. No dynamic testing was performed.
- **Methodology:** Manual white-box code review informed by OWASP Testing Guide v4, OWASP ASVS 4.0, CWE/SANS Top 25, and CVSS v3.1 scoring. Code was reviewed by mapping the application architecture, identifying entry points and trust boundaries, then systematically evaluating each module for common vulnerability classes.
- **Limitations:** This is a static code review only. DVWA is intentionally vulnerable by design — it is a security training application. Findings on the "low," "medium," and "high" security levels are expected by design. The "impossible" level represents the intended secure implementation. This report treats all levels as in-scope to provide a comprehensive security posture assessment, but acknowledges the educational purpose of the application.

---

## 2. Executive Summary

- **Overall risk rating:** **Critical** — The application contains numerous critical and high-severity vulnerabilities across all major vulnerability classes including SQL injection, OS command injection, file inclusion, unrestricted file upload, cross-site scripting, CSRF, broken authentication, and broken access control. This is by design.
- **Key themes:**
  1. **Intentional vulnerability by design:** DVWA is a training tool. The "low" and "medium" levels deliberately contain exploitable flaws.
  2. **Weak password hashing:** MD5 is used universally for password storage, including in the "impossible" (most secure) level.
  3. **Hardcoded credentials and secrets:** Default database passwords and cryptographic keys are embedded in source/config files.
  4. **Configuration backup exposure:** The setup process automatically creates a `.bak` copy of the configuration file containing database credentials.
  5. **Information disclosure:** A `phpinfo()` endpoint is exposed.
  6. **Insufficient security controls on "medium" and "high" levels:** Blacklist-based filtering approaches are consistently bypassable.
- **Most critical findings:** SQL Injection (SQLi-LOW-01), OS Command Injection (CMDI-LOW-01), Unrestricted File Upload (UPLOAD-LOW-01), File Inclusion / Path Traversal (FI-LOW-01), Stored XSS (XSS-S-LOW-01), Authorization Bypass (AUTH-BYPASS-01), and Hardcoded Credentials (CONFIG-01).
- **Immediate priorities:** If this application were to be deployed in any environment beyond an isolated lab, all "low" and "medium" level code paths must be removed, MD5 password hashing must be replaced with bcrypt/Argon2, and the configuration backup mechanism must be disabled.

## 3. Application Overview

### Architecture Summary
DVWA is a PHP/MySQL web application running on Apache, containerized via Docker. It uses a traditional server-rendered PHP architecture with no frontend framework. The application implements a configurable security level system (low, medium, high, impossible) that dynamically loads different source files for each vulnerability module.

### Key Components
| Component | File(s) | Purpose |
|---|---|---|
| Core Framework | `dvwa/includes/dvwaPage.inc.php` | Authentication, session management, CSRF tokens, page rendering |
| Configuration | `config/config.inc.php.dist` | Database credentials, reCAPTCHA keys, security defaults |
| Database Setup | `dvwa/includes/DBMS/MySQL.php` | Schema creation, seed data with hardcoded passwords |
| Login | `login.php` | Authentication entry point |
| Security Settings | `security.php` | User-configurable security level |
| Vulnerability Modules | `vulnerabilities/*/source/{low,medium,high,impossible}.php` | 16 vulnerability categories |
| Docker | `Dockerfile`, `compose.yml` | Container deployment |
| PHP Config | `php.ini` | Enables `allow_url_include` and `allow_url_fopen` |

### Authentication and Authorization Model
- Session-based authentication using PHP sessions with PHPSESSID cookie
- Login via username/password with MD5 hashing (no salting)
- Security level stored in a client-side cookie (`security`), controllable by the user
- Optional authentication bypass via `$_DVWA['disable_authentication']` config flag
- CSRF protection via MD5-based session tokens on some pages
- Authorization checks are inconsistent — some modules check for admin role, others do not
- The "impossible" level adds `HttpOnly`, `SameSite=Strict` cookie flags and session regeneration

### Sensitive Assets / Data Handled
- User credentials (usernames, MD5-hashed passwords)
- Database connection credentials
- reCAPTCHA API keys
- Session tokens
- Uploaded files (stored in web-accessible directory)

### Attack Surface Summary
| Entry Point | Method | Authentication Required |
|---|---|---|
| `login.php` | POST | No |
| `setup.php` | POST | No (creates/resets DB) |
| `phpinfo.php` | GET | Yes |
| `vulnerabilities/*/index.php` | GET/POST | Yes |
| `vulnerabilities/authbypass/get_user_data.php` | GET | Varies by level |
| `vulnerabilities/authbypass/change_user_details.php` | POST | Varies by level |
| `vulnerabilities/api/public/index.php` | REST API | Token-based |
| `vulnerabilities/bac/log_viewer.php` | GET | Yes |
| `hackable/uploads/` | GET (direct access) | No |
| `config/config.inc.php.bak` | GET (direct access) | No |
| `robots.txt` | GET | No |

### Trust Boundaries
1. **Internet → Web Server:** All HTTP inputs (GET, POST, Cookie, Headers) are untrusted
2. **Web Server → Database:** SQL queries constructed from user input cross this boundary
3. **Web Server → OS:** Command injection entry points cross this boundary
4. **Client Cookie → Server Logic:** The security level is stored in a client cookie, meaning the user controls which code path executes
5. **File System:** Uploaded files and included files cross trust boundaries

## 5. Detailed Findings

### [SQLI-01] SQL Injection — Multiple Modules

- **Severity:** Critical
- **CVSS v3.1:** 9.8 (AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H)
- **CWE:** CWE-89 (Improper Neutralization of Special Elements used in an SQL Command)
- **OWASP Category:** A03:2021 — Injection
- **Affected Files/Locations:**
  - `vulnerabilities/sqli/source/low.php` — `$id` from `$_REQUEST['id']` directly concatenated
  - `vulnerabilities/sqli/source/medium.php` — `mysqli_real_escape_string` used but value not quoted in SQL
  - `vulnerabilities/sqli/source/high.php` — `$id` from `$_SESSION['id']` directly concatenated
  - `vulnerabilities/sqli_blind/source/low.php` — `$id` from `$_GET['id']` directly concatenated
  - `vulnerabilities/sqli_blind/source/medium.php` — escaped but unquoted numeric context
  - `vulnerabilities/sqli_blind/source/high.php` — `$id` from `$_COOKIE['id']` directly concatenated
  - `vulnerabilities/brute/source/low.php` — `$user` from `$_GET['username']` directly concatenated
- **Description:** User-supplied input is directly concatenated into SQL queries without proper parameterization. This allows an attacker to inject arbitrary SQL commands.
- **Technical Details:** In the low-level SQLi module, the query is constructed as `"SELECT first_name, last_name FROM users WHERE user_id = '$id';"` where `$id` comes directly from `$_REQUEST['id']`. No sanitization is applied. The medium level applies `mysqli_real_escape_string()` but places the value in an unquoted numeric context (`WHERE user_id = $id`), which is bypassable. The high level reads from `$_SESSION['id']` but still concatenates without parameterization.
- **Evidence from Code:**
  ```php
  // sqli/source/low.php
  $id = $_REQUEST[ 'id' ];
  $query = "SELECT first_name, last_name FROM users WHERE user_id = '$id';";
  ```
  ```php
  // sqli/source/medium.php
  $id = mysqli_real_escape_string($GLOBALS["___mysqli_ston"], $id);
  $query = "SELECT first_name, last_name FROM users WHERE user_id = $id;";
  // Note: $id is not quoted — escape is ineffective for numeric injection
  ```
- **High-Level Abuse Scenario:** An attacker submits a crafted `id` parameter (e.g., `1' OR '1'='1' -- -`) to extract all records, perform UNION-based data exfiltration, or read arbitrary database tables including password hashes.
- **Preconditions:** Authenticated session (any user), security level set to low/medium/high.
- **Impact:** Complete database compromise — extraction of all user credentials, potential for data modification or deletion.
- **Likelihood:** High
- **Remediation:** Use parameterized queries (prepared statements) with PDO as demonstrated in the `impossible.php` implementations. Always bind parameters with proper types. Never concatenate user input into SQL strings.
- **Remediation Priority:** Immediate
- **Validation Notes:** The impossible-level implementation correctly uses PDO prepared statements with `bindParam()` and `PDO::PARAM_INT`.

### [CMDI-01] OS Command Injection

- **Severity:** Critical
- **CVSS v3.1:** 9.8 (AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H)
- **CWE:** CWE-78 (Improper Neutralization of Special Elements used in an OS Command)
- **OWASP Category:** A03:2021 — Injection
- **Affected Files/Locations:**
  - `vulnerabilities/exec/source/low.php` — `$target` from `$_REQUEST['ip']` passed directly to `shell_exec()`
  - `vulnerabilities/exec/source/medium.php` — blacklist removes only `&&` and `;`
  - `vulnerabilities/exec/source/high.php` — expanded blacklist but still bypassable (`|` without space not filtered, note `'| '` is filtered but `|` alone is not)
- **Description:** User input is passed directly to `shell_exec()` for a `ping` command. Metacharacters allow command chaining.
- **Technical Details:**
  ```php
  // exec/source/low.php
  $target = $_REQUEST[ 'ip' ];
  $cmd = shell_exec( 'ping  -c 4 ' . $target );
  ```
  The medium level blacklists `&&` and `;` but not `|`, `||`, backticks, or `$()`. The high level blacklists `'| '` (pipe followed by space) but not `|` without trailing space.
- **Evidence from Code:**
  ```php
  // exec/source/high.php — '| ' is filtered but '|' (no space) is not
  $substitutions = array(
      '||' => '', '&' => '', ';' => '', '| ' => '', '-' => '',
      '$' => '', '(' => '', ')' => '', '`' => '',
  );
  ```
- **High-Level Abuse Scenario:** An attacker provides `127.0.0.1|whoami` (no space after pipe) to execute arbitrary OS commands with web server privileges.
- **Preconditions:** Authenticated session, security level set to low/medium/high.
- **Impact:** Full remote code execution on the web server. An attacker could read/write files, install backdoors, pivot to internal networks, or exfiltrate data.
- **Likelihood:** High
- **Remediation:** Validate input strictly (the impossible level correctly validates IP octets). Avoid passing user input to shell commands. Use language-native functions (e.g., PHP's `escapeshellarg()` combined with strict input validation).
- **Remediation Priority:** Immediate
- **Validation Notes:** The impossible-level correctly validates that input consists of exactly 4 numeric octets before constructing the command.

### [FI-01] Local/Remote File Inclusion

- **Severity:** Critical
- **CVSS v3.1:** 9.8 (AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H)
- **CWE:** CWE-98 (Improper Control of Filename for Include/Require Statement)
- **OWASP Category:** A03:2021 — Injection
- **Affected Files/Locations:**
  - `vulnerabilities/fi/source/low.php` — no input validation on `$_GET['page']`
  - `vulnerabilities/fi/source/medium.php` — blacklists `http://`, `https://`, `../`, `..\\`
  - `vulnerabilities/fi/source/high.php` — requires filename starts with `file` (allows `file://` protocol)
  - `vulnerabilities/fi/index.php` — calls `include($file)` with the processed value
- **Description:** The `page` GET parameter is used in a PHP `include()` call. The low level performs no validation. The medium level's `str_replace` is bypassable with double-encoding (e.g., `....//`). The high level's `fnmatch("file*", $file)` allows the `file://` PHP wrapper.
- **Technical Details:**
  ```php
  // fi/source/low.php
  $file = $_GET[ 'page' ];
  // fi/index.php
  include( $file );
  ```
  With `allow_url_include = on` in php.ini, remote file inclusion is possible on the low level.
- **Evidence from Code:**
  ```php
  // fi/source/medium.php — bypassed by "....//....//etc/passwd"
  $file = str_replace( array( "http://", "https://" ), "", $file );
  $file = str_replace( array( "../", "..\\" ), "", $file );
  ```
  ```php
  // fi/source/high.php — allows "file:///etc/passwd"
  if( !fnmatch( "file*", $file ) && $file != "include.php" ) {
  ```
- **High-Level Abuse Scenario:** An attacker reads sensitive system files (e.g., `/etc/passwd`, application config), includes remote PHP files for code execution, or uses PHP wrapper filters to exfiltrate source code.
- **Preconditions:** Authenticated session. `allow_url_include = on` for RFI (confirmed enabled in `php.ini`).
- **Impact:** Remote code execution (RFI), sensitive file disclosure (LFI), source code leakage.
- **Likelihood:** High
- **Remediation:** Use an allowlist of permitted include files as in the impossible level. Never use user input in `include()`/`require()` calls without strict allowlist validation.
- **Remediation Priority:** Immediate
- **Validation Notes:** The impossible level uses `in_array($file, $configFileNames)` — a proper allowlist approach.

### [UPLOAD-01] Unrestricted File Upload

- **Severity:** Critical
- **CVSS v3.1:** 9.8 (AV:N/AC:L/PR:L/UI:N/S:U/C:H/I:H/A:H)
- **CWE:** CWE-434 (Unrestricted Upload of File with Dangerous Type)
- **OWASP Category:** A04:2021 — Insecure Design
- **Affected Files/Locations:**
  - `vulnerabilities/upload/source/low.php` — no validation at all
  - `vulnerabilities/upload/source/medium.php` — checks client-supplied MIME type only
  - `vulnerabilities/upload/source/high.php` — checks extension and `getimagesize()` but can be bypassed with polyglot files
- **Description:** The low level accepts any file type. Files are stored in `hackable/uploads/` which is web-accessible. A PHP webshell can be uploaded and executed directly.
- **Technical Details:**
  ```php
  // upload/source/low.php
  $target_path = DVWA_WEB_PAGE_TO_ROOT . "hackable/uploads/";
  $target_path .= basename( $_FILES[ 'uploaded' ][ 'name' ] );
  move_uploaded_file( $_FILES[ 'uploaded' ][ 'tmp_name' ], $target_path );
  ```
  The medium level checks `$_FILES['uploaded']['type']` which is client-controlled and trivially spoofable. The high level checks file extension and uses `getimagesize()` but can be bypassed with a PHP file containing valid image headers.
- **High-Level Abuse Scenario:** An attacker uploads a PHP webshell (e.g., `shell.php`) and accesses it directly via `hackable/uploads/shell.php` to execute arbitrary commands.
- **Preconditions:** Authenticated session, write permissions on uploads directory.
- **Impact:** Remote code execution on the server.
- **Likelihood:** High
- **Remediation:** Implement content-type validation server-side, re-encode uploaded images to strip embedded code (as done in impossible level), randomize filenames, store uploads outside the web root, and disable PHP execution in the uploads directory.
- **Remediation Priority:** Immediate
- **Validation Notes:** The impossible level re-encodes images, randomizes filenames, checks CSRF tokens, and validates both extension and content.

### [XSS-R-01] Reflected Cross-Site Scripting

- **Severity:** High
- **CVSS v3.1:** 6.1 (AV:N/AC:L/PR:N/UI:R/S:C/C:L/I:L/A:N)
- **CWE:** CWE-79 (Improper Neutralization of Input During Web Page Generation)
- **OWASP Category:** A03:2021 — Injection
- **Affected Files/Locations:**
  - `vulnerabilities/xss_r/source/low.php` — no encoding of `$_GET['name']`
  - `vulnerabilities/xss_r/source/medium.php` — removes `<script>` tag (case-sensitive, single pass)
  - `vulnerabilities/xss_r/source/high.php` — regex removes `<script>` variants but allows `<img onerror=...>`
- **Description:** User input from the `name` GET parameter is reflected into the HTML response without proper encoding. The `X-XSS-Protection: 0` header is explicitly set, disabling browser-based XSS filters.
- **Technical Details:**
  ```php
  // xss_r/source/low.php
  $html .= '<pre>Hello ' . $_GET[ 'name' ] . '</pre>';
  ```
  The medium level's `str_replace('<script>', '', ...)` is bypassed by `<SCRIPT>` or `<scr<script>ipt>`. The high level's regex filters `<script>` variants but not other HTML event handlers.
- **High-Level Abuse Scenario:** An attacker crafts a malicious URL that, when visited by a victim, executes JavaScript in their browser context to steal session cookies or perform actions on their behalf.
- **Preconditions:** Victim must click a crafted link while authenticated.
- **Impact:** Session hijacking, credential theft, defacement, phishing.
- **Likelihood:** Medium
- **Remediation:** Use `htmlspecialchars()` for all output encoding as in the impossible level.
- **Remediation Priority:** Short-term
- **Validation Notes:** The impossible level correctly uses `htmlspecialchars()`.

### [XSS-S-01] Stored Cross-Site Scripting

- **Severity:** High
- **CVSS v3.1:** 6.1 (AV:N/AC:L/PR:L/UI:R/S:C/C:L/I:L/A:N)
- **CWE:** CWE-79
- **OWASP Category:** A03:2021 — Injection
- **Affected Files/Locations:**
  - `vulnerabilities/xss_s/source/low.php` — both `name` and `message` fields stored without encoding
  - `vulnerabilities/xss_s/source/medium.php` — partial `<script>` removal on `message`, `htmlspecialchars` on `name` bypassed by `name` field `maxlength` attribute
  - `vulnerabilities/xss_s/source/high.php` — regex on `name` field strips `<script>` but allows other vectors
- **Description:** The guestbook stores user-provided `name` and `message` values in the database and displays them to all visitors. Malicious scripts persist and execute for every subsequent viewer.
- **Technical Details:** The low level applies `trim()` and `stripslashes()` on the `message` field and `mysqli_real_escape_string()` for SQL safety, but no HTML encoding. The `dvwaGuestbook()` function in `dvwaPage.inc.php` conditionally applies `htmlspecialchars()` only at the impossible level.
- **High-Level Abuse Scenario:** An attacker injects a persistent script that runs in the browser of every user who views the guestbook, enabling mass session hijacking.
- **Preconditions:** Authenticated session.
- **Impact:** Persistent XSS affecting all visitors — session hijacking, worm propagation, data theft.
- **Likelihood:** Medium
- **Remediation:** Apply `htmlspecialchars()` to all output, use Content-Security-Policy headers, and sanitize input.
- **Remediation Priority:** Short-term
- **Validation Notes:** Impossible level applies proper output encoding in `dvwaGuestbook()`.

### [CSRF-01] Cross-Site Request Forgery (Password Change)

- **Severity:** High
- **CVSS v3.1:** 8.1 (AV:N/AC:L/PR:N/UI:R/S:U/C:H/I:H/A:N)
- **CWE:** CWE-352 (Cross-Site Request Forgery)
- **OWASP Category:** A01:2021 — Broken Access Control
- **Affected Files/Locations:**
  - `vulnerabilities/csrf/source/low.php` — no CSRF protection, password change via GET
  - `vulnerabilities/csrf/source/medium.php` — weak Referer header check (contains bug: `'SERVER_NAME '` has trailing space)
- **Description:** The low-level password change function accepts GET requests with no CSRF token. An attacker can change a victim's password by having them visit a crafted URL. The medium level checks the `HTTP_REFERER` header but has a bug — the key `'SERVER_NAME '` contains a trailing space, making the check always fail.
- **Technical Details:**
  ```php
  // csrf/source/low.php — GET-based password change, no CSRF token
  $pass_new = $_GET[ 'password_new' ];
  $pass_conf = $_GET[ 'password_conf' ];
  ```
  ```php
  // csrf/source/medium.php — broken Referer check
  if( stripos( $_SERVER[ 'HTTP_REFERER' ] ,$_SERVER[ 'SERVER_NAME ']) !== false )
  // Note: 'SERVER_NAME ' has a trailing space — this key doesn't exist
  ```
- **High-Level Abuse Scenario:** An attacker embeds an image tag or link on an external page: `<img src="http://dvwa/vulnerabilities/csrf/?password_new=hacked&password_conf=hacked&Change=Change">`. When the authenticated victim's browser loads it, their password is changed.
- **Preconditions:** Victim must be authenticated and visit an attacker-controlled page. Note: Modern browsers' SameSite cookie defaults may mitigate this.
- **Impact:** Account takeover via forced password change.
- **Likelihood:** Medium (mitigated by modern browser SameSite defaults)
- **Remediation:** Implement CSRF tokens (as in high/impossible levels), use POST method, require current password for changes (as in impossible level).
- **Remediation Priority:** Immediate
- **Validation Notes:** The impossible level correctly implements CSRF tokens, POST method, and current password verification.

### [AUTH-01] Authorization Bypass on Data Endpoints

- **Severity:** High
- **CVSS v3.1:** 8.6 (AV:N/AC:L/PR:L/UI:N/S:U/C:H/I:H/A:N)
- **CWE:** CWE-862 (Missing Authorization)
- **OWASP Category:** A01:2021 — Broken Access Control
- **Affected Files/Locations:**
  - `vulnerabilities/authbypass/change_user_details.php` — no auth check at low/medium/high levels
  - `vulnerabilities/authbypass/get_user_data.php` — no auth check at low/medium levels
- **Description:** The `change_user_details.php` endpoint accepts POST requests with JSON data to modify any user's first name and surname. At low, medium, and high security levels, there is no authorization check — any authenticated user can modify any user's details. Additionally, it contains SQL injection.
- **Technical Details:**
  ```php
  // change_user_details.php — SQL injection via JSON body
  ```

## 6. Attack Path Observations

The following multi-step attack paths are plausible based on the code review:

### Attack Path 1: Configuration Disclosure → Database Compromise → Full Takeover
1. An attacker accesses `/config/config.inc.php.bak` (no authentication required if directory listing is enabled or path is guessable)
2. Obtains database credentials (`dvwa` / `p@ssw0rd`)
3. Connects directly to MySQL if the port is exposed
4. Extracts all MD5 password hashes from the `users` table
5. Cracks MD5 hashes instantly using rainbow tables
6. Logs in as admin

### Attack Path 2: Security Level Downgrade → SQL Injection → Credential Theft → Account Takeover
1. Authenticated attacker sets `security` cookie to `low`
2. Exploits SQL injection in `/vulnerabilities/sqli/` to dump all user credentials
3. Cracks MD5 hashes
4. Logs in as other users including admin

### Attack Path 3: File Upload + File Inclusion → Remote Code Execution
1. Authenticated attacker uploads a PHP webshell via the upload module (low security)
2. Uses the file inclusion module to include the uploaded file
3. Achieves arbitrary code execution on the server

### Attack Path 4: Stored XSS → CSRF → Mass Account Takeover
1. Attacker injects persistent JavaScript via the Stored XSS guestbook
2. Script performs CSRF password change for each visitor
3. All users who view the guestbook have their passwords changed

### Attack Path 5: Authorization Bypass + SQL Injection → Privilege Escalation
1. Non-admin user accesses `/vulnerabilities/authbypass/change_user_details.php`
2. Exploits SQL injection in the JSON body to modify the admin user's details or extract password hashes
3. Escalates to admin privileges

## 7. Positive Security Controls Observed

The following defensive patterns are present in the codebase, particularly in the "impossible" security level:

1. **Prepared Statements (PDO):** The impossible level consistently uses PDO with parameterized queries (`$data->prepare()`, `$data->bindParam()`), correctly preventing SQL injection.

2. **CSRF Token Implementation:** A token-based CSRF protection system (`generateSessionToken()`, `checkToken()`, `tokenField()`) is implemented and used in the impossible level and some higher levels.

3. **Output Encoding:** The impossible level uses `htmlspecialchars()` for XSS prevention in output contexts.

4. **Input Validation via Allowlists:** The impossible level of file inclusion uses `in_array()` against a fixed allowlist. The impossible level of open redirect maps numeric IDs to predefined URLs.

5. **Account Lockout:** The impossible brute force implementation includes failed login tracking, time-based lockout (15 minutes), and proper feedback.

6. **File Upload Hardening (Impossible Level):** The impossible upload handler re-encodes images (stripping metadata/embedded code), randomizes filenames, validates content type server-side, and uses CSRF tokens.

7. **Session Security (Impossible Level):** At impossible level, session cookies use `HttpOnly`, `SameSite=Strict`, and session IDs are regenerated on login.

8. **Default Security Level:** The distribution config defaults to `impossible` level: `$_DVWA['default_security_level'] = 'impossible';`

9. **Docker Security:** The compose file binds to `127.0.0.1:4280` rather than `0.0.0.0`, limiting exposure to localhost.

10. **Current Password Required:** The impossible CSRF module requires the current password to change passwords, preventing unauthorized changes.

- **Block web access to config directory:** Add `.htaccess` deny rules or move config outside web root
- **Remove phpinfo.php** from any non-isolated deployment
- **If deploying beyond isolated lab:** Set default security level to `impossible` (already default in dist config)
- **Disable `allow_url_include`** unless specifically needed for training
- **Rotate all default credentials** (database, user accounts)

### Short-term (30 days)
- **Replace MD5 password hashing** with `password_hash(PASSWORD_ARGON2ID)` across all levels including impossible
- **Update database schema:** Expand `password` column from `varchar(32)` to `varchar(255)`
- **Implement server-side security level storage** (session/database) instead of client cookie
- **Add authorization checks** to all API endpoints (`change_user_details.php`, `get_user_data.php`)
- **Replace CSRF token generation** with `bin2hex(random_bytes(32))`
- **Use `password_verify()`** for password comparison

### Medium-term (90 days)
- **Implement Content-Security-Policy** headers with dynamic nonces across the application
- **Add rate limiting** at the application or web server level
- **Implement security logging** for authentication events, authorization failures, and input validation failures
- **Add HTTP security headers:** `X-Content-Type-Options`, `X-Frame-Options`, `Strict-Transport-Security`
- **Move uploaded files** outside the web root
- **Implement proper session management** with `session_regenerate_id(true)` on privilege changes

### Strategic Improvements
- **Modernize the framework:** Consider using a modern PHP framework (Laravel, Symfony) with built-in security controls
- **Implement automated security testing** in CI/CD (SAST, DAST)
- **Add dependency scanning** for third-party packages
- **Implement audit logging** with tamper-proof storage
- **Consider upgrading from PHP sessions** to JWT or similar stateless tokens with proper signing for the API module
- **Add input validation library** with centralized sanitization/validation rules
